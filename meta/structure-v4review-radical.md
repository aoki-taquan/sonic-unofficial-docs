## 0. 一行結論

**v4 は採用可。前回ラディカル案の主張がほぼ通った形で、これ以上の圧縮（2 タブ・タブ廃止）は逆効果。**
ただし Reference 内 5 カテゴリの**順序と粒度**には微調整余地があり、Phase 1 を最短経路で実施すべき。

## 1. v4 はラディカル簡素化派の理想と一致するか

### 1.1 一致点（前回主張の通った部分）

| 前回 v3 評価での主張 | v4 での反映 | 評価 |

| タブ数 4 → 3 | **3 タブ採用** | ◎ 一致 |
| Verification は独立タブ不要、Reference 末尾セクションで | **`reference/verification/` 採用** | ◎ 一致 |
| Library 命名は曖昧、改名検討 | **「サブシステム」採用** | ○ 日本語化で読者に届く |

| 移行コスト最小化 | **Phase 1 = 1 PR / 30 分** | ◎ 一致 |
| index.md を Hub grid cards 化 | **`index.md` ハブ化採用** | ◎ 一致 |
| Tags プラグイン廃止 | **`related_topics:` frontmatter のみ** | ◎ 一致 |

**前回 v3 評価で挙げた 7 項目中 7 項目が反映済み**。ラディカル派の主張はほぼ完全に通った。

### 1.2 差分（前回案と v4 の違い）

| 軸 | 前回ラディカル案 (3 タブ) | v4 (3 タブ + 5 カテゴリ) | 評価 |

**判定**: v4 は前回ラディカル案の上位互換。Runbooks 復活と日本語命名で A/B 視点を救いつつ、3 タブのシンプルさを保っている。

## 2. それでもまだ削れる箇所はあるか

### 2.1 2 タブ案の検討（Topics + Reference にサブシステム統合）

**仮説**: サブシステム (327 ページ) を Reference 内の 6 つ目カテゴリにして、タブを 2 つに圧縮できないか。

| 観点 | 評価 |
|---|---|
| ページ数バランス | Topics 143 / Reference 166 + 327 + 10 + 3 = 506 → **Reference が肥大化し過ぎ**。1 タブで 506 ページの sidebar はスクロール地獄 |
| 読者の動詞 | サブシステムは「読む」(深い解説)、Reference は「引く」(短い参照)。**動詞が違うものを 1 タブに混ぜると検索動線が壊れる** |
| Hick's Law | 2 タブは確かに最小だが、Reference 内カテゴリが 6 になり sidebar 認知負荷が増える。**タブで圧縮した分が sidebar で増える** |
| デファクト | Kubernetes / Linux カーネル / Ceph 等の大規模 OSS docs は概ね 3-4 タブ。**2 タブは小規模プロダクト (Tailwind / Astro) のパターン**で、656 ページ規模には合わない |

**判定**: **2 タブ案は不適切**。サブシステムは Reference とは別の動詞 (読む) で、独立タブを保持すべき。v4 の 3 タブが下限。

### 2.2 タブ廃止案（sidebar + index.md のみ）

**仮説**: mkdocs-material 検索が強力 (656 ページ全文 + 日本語 separator) なので、タブを全廃して index.md Hub + sidebar だけで運用できないか。

| 観点 | 評価 |
|---|---|
| 検索依存度 | 検索キーワードを持つ読者には機能するが、**初回読者は検索ワードを持たない**。タブは「分野を知る」入口として残すべき |
| index.md への一極集中 | Hub カード 8-10 枚で代替可能だが、**深い階層から戻る導線が弱い**。タブが上部固定で常時アクセス可能なメリットを失う |
| デファクト | Cloudflare 1 タブ等の事例はあるが、彼らも上部に検索バー + 大分類 sidebar を持つ。**タブ廃止は見た目の話で、認知地図は依然 3 分類存在する** |
| モバイル | mkdocs-material のタブはドロワー化されるので、PC のタブ廃止はモバイル UX に影響しない一方、PC の常時露出が消える |

**判定**: **タブ廃止は過剰な引き算**。3 タブは「分野の存在を読者に常時可視化する」最小コストで、ここから削るのは引き算ではなく剥奪。

### 2.3 Reference 内 5 カテゴリの削減

| カテゴリ | ページ規模 | 削減可否 |
|---|---|---|
| CLI | 25 | 必須、削減不可 |
| CONFIG_DB | 66 | 必須、削減不可 |
| YANG | 28 | 必須、削減不可 |
| Runbooks | 10-15 (新設) | **唯一の削減候補**。Topics 章末に戻す選択肢あり |
| Verification | 2-3 + 40 件 discrepancy | 必須、削減不可 (プロジェクト独自価値) |

**Runbooks を削るか**:
- 削るメリット: カテゴリが 4 に減り認知が軽い
- 削るデメリット: A 視点 (運用者) の動線が再び劣化、症状逆引きの場所が「Topics 章末」と分散し検索性が悪化
- **判定**: Runbooks は残すべき。「症状」は仕様引きと並ぶ独立した動詞であり、Reference カテゴリとして妥当

**結論**: 5 カテゴリは下限。これ以上削ると本質を失う。

## 3. Reference 内 5 カテゴリの順序・粒度

### 3.1 提案 v4 の順序
```
① CLI ② CONFIG_DB ③ YANG ④ Runbooks ⑤ Verification
```

### 3.2 ラディカル視点での評価

| カテゴリ | 読者の頻度 | 動詞 | 配置 |
|---|---|---|---|
| CLI | 高 (運用者の日常) | 引く (コマンド名) | **最上位**（妥当） |
| CONFIG_DB | 中 (設計者・実装者) | 引く (テーブル名) | 2 位 |
| YANG | 中 (NMS 連携者) | 引く (モジュール名) | 3 位 |
| Runbooks | 高 (障害時) | 引く (症状) | **2 位推奨** ← 微調整 |
| Verification | 低 (品質メタ情報読者) | 一覧する (横断) | **最下位**（妥当） |

### 3.3 推奨順序

```
① CLI ② Runbooks ③ CONFIG_DB ④ YANG ⑤ Verification
```

**根拠**:
- CLI と Runbooks は「**運用者の日常**」で頻度最高、隣接させて運用者ペルソナの動線を完結させる
- CONFIG_DB と YANG は「**設計者・実装者**」で同ペルソナ、隣接させる
- Verification は「**メタ情報**」でペルソナが異なる、末尾で隔離

**ただし**: この変更は `reference/.pages` の 1 行並べ替えで済むため、Phase 1 の中で同時実施可能。v4 案の順序のままでも実害は小さい (CLI と Runbooks の距離が 2 つあるだけ)。

### 3.4 粒度の妥当性

- CLI 25 / CONFIG_DB 66 / YANG 28 / Runbooks 10-15 / Verification 2-3 + 40
- **CONFIG_DB が他カテゴリの 2-3 倍**で粒度が不均衡だが、これは中身の問題で構造の問題ではない
- Verification の「2-3 ページの hub + 40 件の discrepancy リンク集」という構造は妥当。discrepancy ページ自体は該当 area に置きつつ、`reference/verification/index.md` で集約する設計が良い

## 4. 「これ以上シンプルにすると本質を失う」境界線

### 4.1 死守ライン

| 要素 | 死守理由 |
|---|---|
| **タブ 3 つ** | 2 タブにすると Reference が 506 ページで sidebar 崩壊。タブ廃止は初回読者導線喪失 |
| **Topics とサブシステムの分離** | 動詞 (読む短編 vs 読む詳細) は同じだが粒度が違う。混ぜると Topics の入門性が消える |
| **Reference 内 Verification カテゴリ** | プロジェクト独自価値 (HLD と実装の乖離裏取り)。削ると差別化要素が消える |
| **Runbooks の独立カテゴリ** | A 視点 (運用者) の症状逆引き動線。Topics 章末に戻すと分散して検索性が落ちる |
| **URL 完全維持** | 既存被リンクと検索インデックスの保護 |

### 4.2 譲歩可能ライン

| 要素 | 譲歩理由 |
|---|---|
| Reference 内カテゴリ順序 | `.pages` の 1 行並べ替えで可逆 |
| サブシステム命名（Library / サブシステム / Subsystems） | 表示文字列のみ、URL に影響なし |
| Hub バナーの粒度 | index.md の編集だけで調整可能 |
| `related_topics:` frontmatter の機械追加タイミング | Phase 3 で後追い可能 |

### 4.3 本質を失う領域（やってはいけない圧縮）

- ❌ **タブ廃止** → 初回読者導線喪失
- ❌ **2 タブ化** → sidebar 崩壊または動詞混在
- ❌ **Reference と サブシステム の統合** → 「引く」と「読む」が混ざる
- ❌ **Verification を `_meta/` に戻す** → プロジェクト独自価値の隠蔽
- ❌ **Runbooks を Topics 章末に再統合** → 運用者導線の再劣化（A 視点が再び破綻）
- ❌ **物理 URL 変更を伴う再編** → 既存被リンクと検索インデックスを破壊

## 5. v4 採用判定

### 5.1 採用可否

**採用可（強く推奨）**。前回 v3 評価で主張した 3 タブ案がほぼそのまま通り、追加の Runbooks 復活と日本語化で他視点 (A/B) の指摘も同時に救済された。**v4 は 6 視点の最大公約数解として収束している**。

### 5.2 さらなる圧縮余地

ほぼ無し。検討した 2 タブ案・タブ廃止案・カテゴリ削減はいずれも本質喪失。
**「3 タブ + Reference 内 5 カテゴリ」が下限**。これ以上は引き算ではなく剥奪。

### 5.3 微調整推奨

1. **Reference 内順序**: `CLI → Runbooks → CONFIG_DB → YANG → Verification` に並べ替え（運用者ペルソナと実装者ペルソナを連続配置）
2. **Phase 1 を即実施**: 1 PR / 30 分なので待つ理由がない。`docs/.pages` + `reference/.pages` + `_meta/discrepancies.md` redirect + guides 統合を 1 コミットで
3. **Phase 2 (Runbooks 10-15 件)**: 並走サブエージェント 4-6h で着手。BGP UP しない / VLAN メンバー / FEC / Warm Reboot / DHCP Relay の 5 件を初期セットに
4. **Phase 3 (Verification hub の自動生成)**: `meta/queue/*.json` から `reference/verification/coverage.md` を生成するスクリプトを `scripts/` に追加。Phase 1 と独立で並走可能

### 5.4 v3 → v4 の進化サマリ

| 軸 | v3 (4 タブ) | v4 (3 タブ + 5 カテゴリ) | 改善 |
|---|---|---|---|
| タブ数 | 4 | **3** | Hick's Law 強化 |
| Verification | 独立タブ (3 ページに 1 タブの偏り) | Reference カテゴリ + Hub バナー | 粒度均衡 |
| Runbooks | Topics 章末 troubleshooting | **Reference 内独立カテゴリ** | 運用者導線回復 |
| 命名 | Library (英) | **サブシステム (日)** | 日本語 docs として一貫 |
| Phase 1 工数 | 3 PR | **1 PR / 30 分** | 即実施可能 |
| 不可逆性 | 中 | **低（後戻り 5 分）** | リスク最小 |

---

## 6. 最終ワンライナー

**v4 を即採用し、Phase 1 を 30 分で実施。Reference 内順序のみ「CLI → Runbooks → CONFIG_DB → YANG → Verification」に並べ替え推奨。これ以上の圧縮 (2 タブ / タブ廃止) は本質喪失。構造論争は v4 で終了し、Phase 2 以降の本文品質改善 (D 視点) にリソースを全振りすべき。**
