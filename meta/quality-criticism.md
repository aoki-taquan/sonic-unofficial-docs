# 品質改善 60 ページの徹底批判（反論役レポート）

作成日: 2026-05-11
スコープ: discrepancy 補強 + Topics operations 拡充 合計 60 ページの merge を **読み手の体験変化** という観点から徹底批判する。

---

## 1. 改善 60 ページの問題点（10 個以上）

### 1-1. 「読み手の質問順」で組み直していない
拡充は `show 出力例 → ログサンプル → 異常検出 → 対応コマンド早見表` というセクションを **機械的に追加** しただけ。読み手が実運用で抱く質問の順序（「これは壊れているか？」→「壊れているなら何が原因か？」→「どう直すか？」）と一致していない。情報は増えたがナビゲーションは改善していない。

### 1-2. discrepancy 補強フォーマットの硬直性
`ファイル + 行番号 + 差分 + 影響 + 回避策` の 5 フィールドは **機械生成しやすい型** に最適化されている。読み手にとっては「結局自分のユースケースに影響するのか？」という判断軸が抜けている。例: 影響範囲が「全ユーザー」「特定ベンダー」「特定構成のみ」のどれかが明示されないと判断材料にならない。

### 1-3. スキャナビリティの欠如
+100〜200 行のボリューム増だが、**見出しレベル・コールアウト（!!! warning / !!! note）の使い分けが場当たり的**。読み手が斜め読みで「ここが地雷」を 5 秒で拾える構造になっていない。MkDocs Material の admonition 機能を活かせていない。

### 1-4. 情報密度の上昇 ≠ 質の向上
そもそも誰がどの順番で読むかの **読者モデル** が無いまま情報を詰め込んでも、読み手の認知負荷が増えるだけ。「初めて触る人」「障害対応中の人」「設計検証中の人」で必要な情報は違うが、ページは一律に「全部入り」化している。

### 1-5. AI 量産の人間レビューゼロ
「8 並走で 60 ページ」は技術的偉業のように見えるが、**人間による技術レビューがゼロ**。show 出力例が実機で取られたものか、生成された hallucination か区別がつかない。verifier は HLD との突き合わせはやるが、ユーザビリティレビューは不在。

### 1-6. 誰も読まないページを太らせている可能性
600+ ページ中、Google Analytics 等の閲覧データが無いため、**改善 60 ページが top 10% の流入ページかどうか不明**。trafic 0 のページに +200 行加えても誰にも届かない。

### 1-7. 「discrepancy-found」がカタログ化されていない
discrepancy を各ページに散らしているが、「実装と HLD のズレ一覧」という横断ビューが無い。読み手は「自分が使う機能に既知のズレがあるか」を 1 ページで把握できない。1-3 と同根の構造問題。

### 1-8. operations 拡充が SONiC 固有性を欠く
追加された運用コマンドの多くは `show interface` `show ip bgp` などの **汎用ネットワーク運用知識** で、ベンダー汎用書籍と差別化できていない。「SONiC ならではの落とし穴」（Redis DB 直読み、SAI 状態確認、warm-reboot との相互作用）に踏み込めていない。

### 1-9. 早見表のメンテナンスコスト
コマンド早見表は SONiC master が動くたびに陳腐化する。**maintained-by を AI 再生成に頼ると、ある時点で再生成が止まれば一斉に古びる**。手で書いた解説の方が時間耐性が高い。

### 1-10. PR 単位での比較不能性
60 ページの「改善前/改善後」を読者目線で比較した resolved-issue が無い。before/after の screenshot や読み比べが存在せず、改善効果は **コミット行数でしか測れていない**。

### 1-11. 並走 8 本という運用自体が品質統一を壊す
8 並走で書くと、ページ間のトーン・粒度・admonition 使用ポリシーが揃わない。サイト全体としての一貫性が劣化。

### 1-12. 自己強化ループの匂い
「改善した → KPI（merge 数）が伸びた → 次も同じ手で改善する」という自走ループが自己目的化している。**ループの停止条件が「backlog 枯渇」しかなく、ユーザー満足度を測る exit criterion が無い**。

---

## 2. 方向性が間違っていた可能性

### 2-1. 補強より根本書き直しが先
discrepancy を補強したところで、ベースのページが **HLD 翻訳調のまま** ならば読みにくさは変わらない。先にやるべきは「読者が知りたい順」で各 concept.md を書き直す再構成。それを後回しにして付録を厚くしている。

### 2-2. operations 拡充より concept 改善
運用コマンド早見表を増やす前に、「そもそもこの機能は何のためにあるのか」「どういう設計思想か」を語る concept ページが薄い。これは AI でも書きにくい部分だから後回しにされた可能性がある。**書きやすいところから書いている**という生産バイアス。

### 2-3. 読者データなしで進めている
600+ ページのうち何ページに人が来ているかのデータがゼロ。GA / Plausible / サーバーログ何も無い状態で「どこを改善すべきか」を判断できるはずがない。**根拠なく動いている**のが最大の問題。

---

## 3. 推奨する次行動

### 3-1. すべての PR を一時停止
構造改善も本文改善も止める。改善 PR を merge しても効果を測れないなら、merge するだけ git 履歴を汚す。

### 3-2. 実ユーザーフィードバックの取得に全振り
- GitHub Pages にアクセス解析（Plausible / Goatcounter / GA4）を入れる
- README に「読みにくい箇所を issue で教えてください」テンプレを置く
- SONiC コミュニティ Slack / メーリスに「日本語ドキュメント書いているが、欲しい章ある？」と投げる
- 1〜2 名の SONiC ユーザーに 30 分インタビュー

### 3-3. データが出るまで PR を 1 件も merge しない
最低 2 週間 traffic データを取り、上位 20 ページのみを改善対象に再選定する。それ以外は触らない。

### 3-4. ループ暴走シグナルの認識
「backlog があるから書く」「並走できるから並走する」は、いずれも **読者起点ではない**。CLAUDE.md の自走モードと矛盾するが、自走の方向性を決めるのは読者データであり、無いなら止まるのが正しい自走。

---

## 4. 暴走シグナル（このリポジトリ運用へのメタ批判）

- **シグナル A**: バッチ #1〜#11 で量だけ伸び、ユーザーフィードバックの記録が `meta/` のどこにも無い。
- **シグナル B**: discrepancy 補強の連発は「AI が自分で見つけた問題を AI で直す」自己完結ループ。第三者の視点が無い。
- **シグナル C**: `meta/quality-criticism.md` がこの分量で書ける（= 批判材料がいくらでもある）こと自体が、品質改善が表層的だった証拠。

---

## 5. 結論

60 ページの改善は **量としては前進だが、読み手体験としては未検証**。「改善」と呼べる根拠が PR 行数しか無く、読者起点の根拠ゼロ。次の正しい一手は「PR を増やすこと」ではなく「読者データを取ること」。それまでこの reviewer/writer ループを止めることを強く推奨する。
